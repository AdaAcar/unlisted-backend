### Traps

- **`db/migrations/0001_guards.sql` is hand-written and load-bearing.** It holds every invariant Drizzle cannot express from the schema: the FK from `message_thread.plan_id` to `plan.viable_plan_key` (a `STORED` generated column that equals the plan id only while `viable_at IS NOT NULL`, with a `UNIQUE` constraint — this is what makes "no thread on a non-viable plan" structural rather than a forgettable check); the `viable_plan_key` column and its unique constraint; `message_thread_min_participants_chk` (`participant_count >= 3`); the `set_updated_at` trigger + per-table triggers; `enforce_plan_guards()` (mode immutability + `viable_at` latch + set-time floor); the `audit_log` append-only triggers; restricted-column `COMMENT`s. A `drizzle-kit generate` will not see any of this. Do not let a regeneration try to "add" or "drop" these, and if you change the schema, re-check that `0001_guards.sql` still applies cleanly after the new `0000`.
- **`viable_at` latch semantics — the single most likely thing to get wrong.** `viable_at` is set the first time `confirmed_total >= MIN_PLAN_TOTAL` and **never clears** (`enforce_plan_guards()` rejects clearing it). It means *"introduction has occurred"* — the thread, messages, and mutual visibility that follow are permanent and are never undone. Whether the plan **proceeds** is a *separate, live* question: at `starts_at`, if `confirmed_total < MIN_PLAN_TOTAL` the plan auto-cancels regardless of `viable_at` being set. A latched plan that dropped to two confirmed does not meet — it cancels first. The invariant protects the event, not the introduction. Both halves of `docs/modes.md` are correct; they describe these two different things.
- **`MIN_PLAN_TOTAL` (`3`) appears in SQL exactly twice**, both in `0001_guards.sql`, each annotated `/* MIN_PLAN_TOTAL: keep equal to lib/config.ts */`: the `viable_at` set-time floor in `enforce_plan_guards()`, and `message_thread_min_participants_chk`. `tests/unit/migration-min-plan-total.test.ts` parses both and asserts each equals `config.MIN_PLAN_TOTAL` and that there are exactly two. If you touch either literal, keep the annotation and keep them equal to `lib/config.ts`. SQL cannot import the TS constant; that annotation is the only checkable link.
- **No Assembly table exists and none should.** `docs/data-model.md` describes an `Assembly` entity; it is deferred and explicitly not built. The three-person floor plus the viability gate cover what it would have done. Do not add assembly tables, endpoints, or workers.
- **`data-model.md` and `api.md` predate the two-mode design.** Where they disagree with `docs/modes.md` (Plan `mode` / `viable_at` / `applications_closed_at`, the Assembly table, the `MessageThread` rule stated in participant-count terms, the `approve` endpoint), `modes.md` wins — this is settled, do not re-ask.
- **`agent-rules.md` §3's "A message thread requires two circle references and a viable plan" is superseded — user-authorized, C8.** `message_thread` is now plain plan-scoped: migration `0012` dropped `circle_a_id` / `circle_b_id` and their `<>` check. `agent-rules.md` is read-only so the sentence still stands there; this note is the deviation record a future agent must find. **Why it is safe:** the two-circle rule was never the anti-dyad guarantee — `MIN_HOST_CIRCLE = 1` makes circles of one legal, so two distinct one-member circles satisfy `circle_a_id <> circle_b_id` and *are* a two-person thread. A dyad has only ever been barred by `message_thread_min_participants_chk` (`participant_count >= 3`) plus the FK to `plan.viable_plan_key`. **What replaces it:** `participant_count` is now trigger-maintained from `plan_participant_introduction` (0012) — set from the ledger on INSERT, resynced when the ledger grows — so `>= 3` is a property of the data, not a number a caller is trusted to write. Full reasoning in Decisions C8.
- **`db/migrations/0002_rls.sql` is a custom, load-bearing migration.** Drizzle generated its journal entry and snapshot metadata; the SQL body is deliberately hand-authored. It creates global roles, security-definer visibility helpers, all RLS policies, ownership/grants, and the `audit_log` revocation. Do not regenerate or edit it after application; add a new migration for policy changes. The app-layer authored visibility source remains `db/scope/visibility.ts`, and integration tests assert the SQL mirror behaves identically for the implemented repositories.
- **`0004_a3_corrections.sql` deliberately supersedes `0002` without editing it.** It fails before other work if a pre-ledger viable plan exists, because no exact introduction backfill can be inferred. It clears the known passwords and LOGIN attributes from capability roles, removes admin `BYPASSRLS`, replaces broad mutation grants/policies with exact reads, and installs the viable-key ledger FK, locked trigger-only population, append-only guards, and forced RLS. `0003` is generated; `0004` is custom. Never edit either after application.
- **`0005_migration_ownership.sql` is the post-bootstrap migration boundary.** It transfers the `drizzle` schema, `drizzle.__drizzle_migrations`, and its sequence to `unlisted_migrator`, grants the database/schema and ledger privileges Drizzle actually needs, and excludes application/admin capabilities. Do not edit `0000`–`0005` after application; add a later migration.
- **`0006_audit_append.sql` restores a narrow `unlisted_app` `INSERT` on `audit_log`**, superseding (not reversing) `0004`'s blanket revocation for that one table/verb. `unlisted_admin` gets nothing on `audit_log`. Never edit `0000`–`0006` after application; add a later migration.
- **`0006_audit_append.sql`'s trailing `REVOKE SELECT, UPDATE, DELETE, TRUNCATE ON public.audit_log ...` is not merely redundant with `0004`'s blanket revocation — the `TRUNCATE` half is load-bearing.** `TRUNCATE` does not fire row-level triggers, and row-level security does not apply to it at all (Postgres applies RLS to row-granular DML only). If `unlisted_app` or `unlisted_admin` ever held `TRUNCATE` on `audit_log`, that grant would bypass `audit_log_no_update`/`audit_log_no_delete` entirely — the append-only guarantee would have a hole no existing trigger-based test could catch, because `TRUNCATE` never reaches the trigger machinery those tests exercise. (A5 considered adding this as a comment in `0006_audit_append.sql` itself — the migration is already applied, and hand-editing even a leading comment block risks a drizzle `__drizzle_migrations` hash mismatch on any persistent DB per the general rule above; recording it here instead avoids that risk. Do not edit `0006`'s SQL to add this note.)
- **`SET ROLE`/`SET LOCAL ROLE` fully drops superuser status and BYPASSRLS for the remainder of that scope — RLS re-applies exactly as if you had logged in as the target role.** `FORCE ROW LEVEL SECURITY` on `audit_log` then means the table **owner** (`unlisted_migrator`, non-superuser) has no visibility into existing rows for `UPDATE`/`DELETE` once you `SET ROLE` to it, because it has no `SELECT`/`UPDATE` policy on `audit_log` at all — the statement silently matches **zero rows** rather than erroring, so the append-only triggers never fire and a test written that way passes for the wrong reason (RLS filtered the row out, not the trigger blocking it). A Postgres **superuser** session, by contrast, always bypasses row security entirely, `FORCE ROW LEVEL SECURITY` included — so proving "even the owner is blocked by the trigger" means issuing the `UPDATE`/`DELETE` directly as the superuser test pool (`t.pool`, already trusted, no new import), not via `SET ROLE unlisted_migrator`. `tests/integration/audit-log.test.ts` does this and documents why inline. This generalizes: any future adversarial test against a `FORCE ROW LEVEL SECURITY` table's owner privileges needs the same care.

### Rationale that must not be "simplified" away

- **Runtime role and actor scope are transaction-local.** `withActor` begins a transaction, runs `SET LOCAL ROLE unlisted_app`, then transaction-local `set_config` calls. The named admin executor begins a transaction and runs `SET LOCAL ROLE unlisted_admin`. Never use `SET SESSION` for either roles or GUCs: pooled connections are reused and would leak authority or identity between requests.
- **Attendance transitions lock the plan first.** Every current and future application/domain attendance transition must acquire the plan row lock before changing attendance state. Ledger triggers also lock the plan before checking viability, selecting eligibility, or inserting, but trigger ordering is not permission to perform application-first domain writes. The locked plan transaction owns counter changes, the viability latch, and introduction population together.
- **`withActor` (A3) must wrap read-only repository calls in a transaction too**, for the same reason — the GUC is transaction-scoped, so without the transaction RLS does not engage and the query is unscoped.
- **The `viable_plan_key` FK-to-generated-column mechanism was verified on Postgres 16 specifically.** It relies on FK-to-a-`UNIQUE`-generated-column, which PG has supported since 12, but no other major version has been exercised here. If the Postgres version changes, re-run the A2 integration suite.
- **`application.state` is one enum spanning both mode machines, gated by a mode-scoped `CHECK`** (see Decisions/A2). Consequence: adding a new state value later needs `ALTER TYPE application_state ADD VALUE …`, which **cannot run inside a transaction** on Postgres — such a migration must be its own non-transactional step. Do not "clean this up" into two enums without re-checking every `CHECK` and view that depends on the union.
- **`lib/config.ts` reads nothing from the environment, by decision.** Do not add a `process.env` fallback "for flexibility" — `MIN_PLAN_TOTAL` in particular must not be movable by whoever controls the deployment.
- **`recordAuditEntry` (A4) joins the caller's transaction; it never opens one.** It takes the executor `withActor` (or a system-actor equivalent) already handed its callback, as a parameter. This is what makes A4's "done when" — a rolled-back caller transaction leaves no audit row — true by construction, not by discipline. Do not "simplify" it into a self-contained helper that opens its own transaction; that would silently break the guarantee.
- **`ip_hash`/`user_agent_hash` are keyed HMAC-SHA-256 (`lib/hash.ts`, `AUDIT_HASH_SECRET`), not a plain digest.** An unkeyed SHA-256 of an IPv4 address is reversible by brute force in seconds (2^32 addresses) — a plain hash would still be personal data in another form, which agent-rules section 3 forbids. `env.auditHashSecret` requires at least 32 bytes and throws (fails audit writes closed) if unset or shorter — a plausible-looking placeholder like `changeme` cannot silently produce hashes. **Rotating `AUDIT_HASH_SECRET` breaks correlation with every historical `audit_log` row** (the same IP/UA will hash differently under a new key) — do not rotate it expecting continuity, and do not treat it as an operational knob to change casually.
- **`audit_log_app_append`'s `WITH CHECK` (0006) ties `actor_role` to `actor_id` in both directions, not just one.** The A3-era policy 0004 dropped only pinned `actor_id = app_current_actor_id()` for a non-null id. Pinning only that leaves a gap: a user's own transaction could still label its own row `actor_role = 'system'` while keeping its own (honest) id — the id wouldn't be forged, but the role would misrepresent what kind of action it was. The 0006 policy additionally requires `actor_role = 'system' ⟺ actor_id IS NULL`, closing that. There is no moderator GUC yet — moderator capability is not an actor field until D4 (A3 decision, unchanged) — so the policy cannot pin `actor_role = 'moderator'` to a distinct credential; an app-role caller can currently self-label an action `'moderator'`, which only adds an obligation (`audit_log_moderator_reason_chk` then requires `reason`) and grants no capability. Infrastructure config (DB/Redis URLs, session secrets) will live in a separate env module added by the task that first needs it, and will never be merged into `config`.

- **Vitest `@/*` alias is a direct `resolve.alias`, not `vite-tsconfig-paths`.** The package is not `"type": "module"`, so Vitest loads `vitest.config.ts` through a CommonJS `require`; `vite-tsconfig-paths` is ESM-only and blew up under `require`. If aliases ever multiply, revisit via `vitest.config.mts` + `vite-tsconfig-paths`.

### A2

- **`viable_at` latch semantics — the single most likely thing for a future session to get wrong.** Both halves of `docs/modes.md` are right; they describe two different things.
  - `viable_at` **latches** on first crossing (`confirmed_total >= MIN_PLAN_TOTAL`) and **never clears**. It means *"introduction has occurred"*. You cannot un-introduce people — the thread stays, messages stay, mutual visibility stays. Enforced by the `enforce_plan_guards()` trigger, which rejects any `viable_at` → NULL update.
  - Whether the plan **proceeds** is evaluated **live**. At `starts_at`, if `confirmed_total < MIN_PLAN_TOTAL` the plan auto-cancels, regardless of `viable_at` being set. A latched plan that has dropped to 2 confirmed does not "meet".
  - Between a post-viability drop and `starts_at`, the plan is recoverable: the freed spot reopens applications if they had closed on spots-filled.
  - Net: **no dyad ever meets, because the plan cancels before it can.** The invariant protects the event, not the introduction.
- **ULID identifiers stored as `varchar(26)` text, not native `uuid`.** Debuggability — logs, `psql`, and error messages show the real, sortable ULID. Costs ~10 bytes/key over `uuid`; view models never expose raw IDs regardless. A Crockford-base32 `CHECK` on every id-bearing column is the constraint-level expression of "all IDs are ULIDs".
- **"No thread on a non-viable plan" is a foreign key to a generated column, not a trigger.** `plan.viable_plan_key` is `GENERATED ALWAYS AS (CASE WHEN viable_at IS NOT NULL THEN id END) STORED`, with a `UNIQUE` constraint; `message_thread.plan_id` is an FK to it. A thread for a non-viable plan has no FK target and the insert fails. Purely declarative, always-on, cannot be forgotten the way a trigger check could. It relies on `viable_at` being a monotonic latch (above) so the key never un-sets under a live thread; a secondary trigger enforces that monotonicity. `drizzle-kit` cannot emit an FK to a generated column, so `viable_plan_key`, its unique constraint, and this FK live in `0001_guards.sql`.
- **`plan.held_count`.** Planned-mode invitations place a soft hold on a spot. The capacity ceiling is `accepted_guest_count + held_count <= open_spots` (DB `CHECK`), not `accepted <= open_spots`. Without the held term, over-invitation would let two applicants accept the same spot. The column and its `CHECK` are in the schema now, deliberately, because altering a capacity constraint once there is production data is exactly what we do not want to do.
- **Viability is a denormalised counter pair + the latch timestamp**, written only inside the plan-row-locked transaction that changed attendance. `confirmed_total` is a stored generated column (`confirmed_host_count + accepted_guest_count`). Not computed-on-read (the FK needs a stored target); not a generated `viable_at` (it must be a first-crossing timestamp and a latch).
- **`MIN_PLAN_TOTAL` literal `3` appears exactly twice in SQL**, both in `0001_guards.sql`, each annotated `/* MIN_PLAN_TOTAL: keep equal to lib/config.ts */`: the `viable_at` set-time floor in `enforce_plan_guards()`, and `message_thread_min_participants_chk`. `tests/unit/migration-min-plan-total.test.ts` parses both and asserts `=== config.MIN_PLAN_TOTAL`. SQL can't import the TS constant; this annotation is the single checkable link. `message_thread.participant_count`'s `>= 3` check is therefore defined in `0001_guards.sql`, not in the Drizzle table — the one place `db/schema/` is not the source of truth.
- **Native Postgres enums** (`pgEnum`), not text + `CHECK IN (…)`, so "valid state enums" is a DB guarantee. `application.state` is the union of both mode machines; a mode-scoped `CHECK` keeps `approved` out of planned and `invited`/`shortlisted`/… out of tonight.
- **`plan.venue_type` and `plan.district` are denormalised from the venue** so the discovery query filters without a join. `district` is specified by `docs/data-model.md`; `venue_type` is the same rationale applied to the C4 type filter.
- **`docs/data-model.md`'s "explicit transition log" = the `audit_log`** (before/after state per state-changing action). No per-entity transition tables.
- **`lib/env.ts` moved to Zod in A3.** `zod` is an exact direct dependency. Infrastructure values remain lazy getters, so importing the module never throws; required role URLs fail only when accessed. `lib/config.ts` remains entirely separate and environment-free.
- **`vitest.config.ts` sets `fileParallelism: false`.** Integration tests drop/recreate the `public` schema of one shared test DB; parallel files would clobber each other. Suite is small; serial costs nothing. Revisit with per-file databases if the suite grows.

### A3

- **Repository restructure of the instruction files.** `CLAUDE.md` sections 1–8 → `docs/agent-rules.md`; sections 9–11 → this file (`docs/state.md`); `todo_claude.md` → `todo_agent.md`; `AGENTS.md` and `CLAUDE.md` are now identical redirect stubs. Rules read-only in `agent-rules.md`; living record here.
- **Q1 — unscoped queries are made impossible by transaction-local capability activation plus forced RLS.** Runtime login identities are separate, secret-backed, and `NOINHERIT`; they have no useful access before `SET LOCAL ROLE`. `withActor` activates `unlisted_app` and actor GUCs transaction-locally. The named admin executor activates `unlisted_admin` transaction-locally. Capability roles are `NOLOGIN`; application and admin each have SELECT on exactly `user`, `block`, `circle_member`, `plan`, `application`, and `application_member`, with no runtime ledger access or table mutation. Static trust is an exact filename allowlist.
- **The old admin `BYPASSRLS` decision is explicitly superseded.** `unlisted_admin` is now `NOLOGIN`, `NOBYPASSRLS`, and read-only. Its six `USING (true)` SELECT policies exist only for `loadActorByUserId` and the existing security-definer user/circle/plan/application visibility helpers. Least privilege is preferred over a general runtime escape hatch; migrations use the separate `unlisted_migrator` capability through a secret-backed deployer and explicit `SET ROLE`.
- **Migration credential cutover is explicit and one-way.** A privileged one-shot bootstrap credential runs `pnpm db:migrate -- --bootstrap` through `0005` exactly once before application traffic. `0004` clears predictable passwords and disables login on capability roles; `0005` hands Drizzle bookkeeping to `unlisted_migrator`. Infrastructure then provisions a secret-backed `NOINHERIT` deployer login with only migrator membership. Every later `pnpm db:migrate` authenticates as that deployer and executes `SET ROLE unlisted_migrator` on its dedicated, non-pooled connection. Integration tests create test-only `NOINHERIT` logins after checking the post-migration capability-role state; they never re-enable LOGIN on capability roles.
- **Q2 — block + enforcement filters are composed once, applied everywhere, reimplemented never.** `db/scope/visibility.ts` exports `blockPredicate(actorId, counterpartyUserIdExpr)` (bidirectional `NOT EXISTS` over `block`), `enforcementPredicate(...)`, a declarative `VisibilitySpec` per table (how to reach the counterparty user id — column or correlated join path), and `applyVisibility(qb, actor, spec)` which `AND`s them in as correlated `EXISTS`/`NOT EXISTS` subqueries (independent of SELECT list / joins / grouping). The chokepoint applies it automatically for the table being queried; repo functions only add business filters. RLS carries the same block + standing rules independently as its `USING` predicates, cross-referenced in comments to `visibility.ts` as the authored source. `restricted` standing: hidden from other actors' feeds, visible to self. `suspended` / `banned`: same. The finer "affected parties" nuance is A5/D4.
- **Q3 — the `Actor` shape, and its origin before B1 exists.** `UserActor = { kind: 'user'; id; verificationState; standing }`; `SystemActor = { kind: 'system'; label }`; `Actor` is the union. No precomputed block set on the actor — blocks are a live correlated subquery keyed on `actor.id`. A3 ships the type + `SYSTEM_ACTOR` + `loadActorByUserId(userId)` (reads `id`, `verification_state`, `standing` from `user` — a narrow named data read, not authentication). Tests build `UserActor` literals from seed rows. B1 later adds `getSessionActor(request)` in front of `loadActorByUserId`; the `Actor` shape and the loader do not change. Repositories depend only on the `Actor` interface, never on how it was produced. Moderator capabilities are not an actor field yet (D4).
- **A3 repository breadth: `plans` and `users` only.** They prove the pattern and satisfy the "done when". Phase-C tasks build `circles` / `applications` / `threads` / `messages` repositories against the same infrastructure. No thin stubs for the others.
- **Profile context is split into review visibility and durable introduction visibility.** Before viability, active hosts and applicants can see one another for review, but applicants cannot see other applicants. Guest-to-guest visibility requires both users in `plan_participant_introduction` for a common viable plan. Initial population is the active host set plus accepted planned solo users, accepted members of compatible (`invited`/`accepted`) planned circle applications, and solo/included-member users of approved tonight applications. Rows never disappear after withdrawal, removal, or a live-total drop. Block and enforcement filters still override the read without deleting history.

### A6

- **The plan machine is a single reducer, `transitionPlan(snapshot, action) -> snapshot`, throwing `DomainError` on any invalid state/action/mode/guard combination.** A reducer over an explicit `PlanAction` union (not a result-union return) was chosen over separate per-transition functions because it makes the state × action space exhaustively enumerable and testable from outside the module (`tests/unit/domain-plan.test.ts` loops every `(state, mode, action)` triple), and because throwing keeps call sites (and tests) as a single `expect(() => …).toThrow(DomainError)` rather than a discriminated-union unwrap at every call site. - **`PlanSnapshot` carries `confirmedHostCount`, `acceptedGuestCount`, and `heldCount` as three separate fields, not a single `confirmedTotal`.** The capacity ceiling from A2 (`accepted_guest_count + held_count <= open_spots`, the DB `CHECK` `plan_capacity_ceiling_chk`) is a guest-only constraint that a merged total cannot express. `confirmedTotal()` is a derived helper (`confirmedHostCount + acceptedGuestCount`), computed on demand rather than stored redundantly in the snapshot, mirroring the DB's generated column but without a second field that could drift from its inputs in a hand-built test fixture.
- **The planned-mode invitation soft hold is modeled as four plan-machine actions — `invite` (places the hold), `declineInvitation` / `expireInvitation` (release it), `acceptInvitation` (converts held → accepted) — each mode-gated to `planned` and guarded by the capacity ceiling.** Tonight mode gets a distinct `approve` action, mode-gated to `tonight`, that adds directly to `acceptedGuestCount` with no hold step at all — matching "no invitation or confirmation states" structurally: tonight snapshots can still carry a `heldCount` field (it is part of the one shared `PlanSnapshot` shape), but no tonight-reachable action ever writes a nonzero value into it. - **`invite` (placing a new hold) is valid only from `published`, not `applications_closed`; `declineInvitation` / `expireInvitation` / `acceptInvitation` (resolving an existing hold) are valid from either.** New invitations should not go out once applications have closed, but a hold placed before closure must still be able to resolve (decline, expire, or convert to accepted) up to `starts_at`.

- **The stubbed credential is `authenticate({ userId }) -> userId | null`, not an interface with a swappable implementation.** `todo_agent.md` says B1 builds session lifecycle "behind a stubbed `authenticate(credential) -> userId` port — the same pattern B2 uses for the KYC vendor," but B2's actual vendor-agnostic interface doesn't exist yet to mirror, and there is only one implementation here. The added `SELECT` is self-scoped by the same RLS predicate (`user_id = app_current_actor_id()`) as insert/delete, so it does not let the app role read any other user's session; the "narrow, not broad" property the task asked for is preserved, just not at the exact three-privilege shape first proposed.

- **Bearer tokens are hashed with unkeyed SHA-256, not `lib/hash.ts`'s keyed HMAC.** `lib/hash.ts`'s keyed HMAC exists because an IP address has a small enough space (2^32) to brute-force an unkeyed digest. Lives in a new `lib/sessionToken.ts`, not `lib/hash.ts`, since the two have different threat models even though both produce hex digests.
- **`SESSION_TTL_SECONDS` (30 days) lives in `lib/sessionToken.ts`, not `lib/config.ts`.** `lib/config.ts` is asserted by `tests/unit/bootstrap.test.ts` to be *exactly* the agent-rules section-5 product parameters; a session TTL is neither one of those nor read from the environment, and adding it there would have broken that test's actual intent (pinning config.ts against a read-only doc) rather than genuinely extending it. It lives with its one caller instead of in a shared module for a value nothing else uses yet.
- **`expires_at` and a TTL check were added to the session table and lookup query**, per explicit user direction when asked (the alternative — no expiry, revocation-only — was the original proposal). Sessions are otherwise unbounded in the schema; nothing currently *shortens* a live session's expiry (no sliding-window refresh on activity) — see Known gaps.
- **Table ownership needed an explicit `ALTER TABLE session OWNER TO unlisted_migrator`, unlike an assumption going in.** The integration test harness runs migrations directly via drizzle's `migrate()` as the raw Postgres superuser, not through `unlisted_migrator` via `SET ROLE` the way `db/migrate.mjs` does for real deployments — so a brand-new table's owner is whoever's session ran `CREATE TABLE`, not automatically `unlisted_migrator`, even after the 0005 migration-ownership cutover. Every prior table got this explicitly (0002 for the original 13, 0004 for `plan_participant_introduction`); `0006` didn't need it only because `audit_log` already had the right owner from 0002/0004. Its value is provider/credential abstraction and none exists yet; its own routing conventions (`/api/auth/*`) don't match `docs/api.md`'s literal `POST|DELETE /auth/session` / `POST /auth/recover`, and its built-in session/rotation model doesn't map cleanly onto "kill one session, leave the others" without working against the library. ### B2

- **Encryption at rest for `identity_hash`/`verification_ref`: keyed hash + column-level access control, not pgcrypto or an app-layer envelope.** Asked per agent-rules section 7 (a security measure named as an open decision); user chose this option explicitly. `identity_hash` is a keyed HMAC-SHA-256 of the vendor's identity reference under a *new*, dedicated `IDENTITY_HASH_SECRET` (`lib/identityHash.ts`/`lib/env.ts`) — deliberately not `AUDIT_HASH_SECRET`: different purpose and a different rotation cost (rotating either breaks a different kind of correlation). Both columns lose their table-wide `SELECT` grant (migration `0008`, superseding 0004's blanket grant for this one table, same pattern as 0006 superseding 0004 for `audit_log`); `identity_hash` gets `SELECT` nowhere at all (nothing ever reads it back — the `UNIQUE` index enforces the ban-durability collision inside Postgres, not application code), `verification_ref` keeps it for `unlisted_app` only (needed for the webhook's `WHERE verification_ref = ...` match — Postgres requires `SELECT` on any column a `WHERE` clause filters on, same reasoning as B1's session `token_hash` grant). Key-management cost, named to the user before this was chosen: `IDENTITY_HASH_SECRET` is a local-dev secret today, the same as `AUDIT_HASH_SECRET` — there is still no KMS or hosting target, so real key custody remains unsolved; rotating it breaks ban-durability correlation for every already-hashed identity (a re-verified banned user's new hash would no longer collide with their old one). No on-disk encryption exists for either column — only access-control-layer protection. Real encryption (pgcrypto) was explicitly declined as costing more (a symmetric key with the same custody problem, plus `identity_hash`'s `UNIQUE` index would need to work against ciphertext or a separate blind index) for a benefit this codebase's threat model doesn't yet need. Revisit if a hosting target/KMS decision makes pgcrypto cheap, or if `verification_ref`'s exposure (not a hash, so not covered by the non-reversibility argument) ever needs real encryption rather than access control.
- **The webhook's write authorization: column-scoped `GRANT` + a dedicated system-actor RLS policy + a `BEFORE UPDATE` trigger, not a policy alone.** Asked per agent-rules section 7 (the webhook's write path had no existing pattern to follow). Discovered while implementing that `0004_a3_corrections.sql` had already **dropped** `0002_rls.sql`'s original `user_actor_scope` (`FOR ALL`) policy and replaced it with `user_app_read` (`SELECT`-only) — so the concern named when this was proposed (a second permissive policy losing to an existing permissive `FOR ALL` one under Postgres's OR-combination semantics) turned out not to be live: there was no other `UPDATE` policy on `"user"` left to collide with. `user_system_verification_write` (migration `0008`) is therefore the *only* `UPDATE` policy on `"user"`, `USING`/`WITH CHECK` both `app_current_actor_id() LIKE 'system:%'` — a real user-actor transaction can never satisfy it regardless of what it is granted. The column-scoped `GRANT UPDATE (verification_state, age, identity_hash, verification_ref)` limits *which columns*; the policy limits *which actor*. The `BEFORE UPDATE` trigger (`enforce_verification_columns_system_only`, mirroring `audit_log`'s append-only guard) is additional, deliberate belt-and-suspenders: it protects these four columns specifically even if some future migration ever adds a broader `UPDATE` policy back onto `"user"` for unrelated (non-verification) columns, since RLS's OR-combination would otherwise let a broader future policy silently widen access to these columns too — the trigger holds regardless of how many policies exist. `startVerification` (marking a user `'pending'` at `POST /verification/start`) also runs as `SYSTEM_ACTOR` for the same reason, even though a real session request triggers it — the trigger does not distinguish "who authorized this" from "whose transaction GUC is doing the write".
- **`completeVerification` matches solely by `verification_ref`, with no separate lookup step.** A new `UNIQUE` index (`user_verification_ref_uq`) guarantees at most one row can match, so the same statement that finds the row also writes it (`RETURNING id` hands the matched user's id back for the audit entry) — no TOCTOU window, no admin-executor lookup needed. `verification_ref` is cleared unconditionally in the same statement: a vendor session is spent whether verification succeeds or fails, and cannot be replayed.
- **`age`/`identity_hash` are only overwritten on a `'verified'` outcome.** Found while testing: an already-verified user who starts (and fails) a second verification attempt must not have their existing, good values silently nulled out by the failed attempt's write. Implemented as two distinct SQL statements (verified vs. failed), not one statement with a conditional self-reference (`identity_hash = identity_hash` to "keep the existing value") — that would need `SELECT` on `identity_hash`, which `unlisted_app` deliberately does not have.
- **The feature flag lives in `lib/env.ts`, defaults to `'stub'` when unset.** Asked per agent-rules section 7 (both placement and default were confirmed rather than assumed); user chose the default explicitly. `env.verificationVendor` throws for any value other than `'stub'` — there is no real vendor yet for another value to mean anything.
- **Erasure-versus-ban durability is out of scope, confirmed with the user before starting.** `identity_hash` is exactly the field `docs/security.md`'s open legal question (line 108) and `todo_agent.md` E2 turn on; B2 stores it for ban durability and builds nothing about erasure, retention, or deletion. Untouched, per the user's explicit confirmation.

- **Q1 — the `circle.lead_user_id` ↔ `circle_member(role='lead', status='active')` invariant: partial unique index + authorize off `circle_member`, no deferred trigger.** The A2 known gap named C1 as owner of this cross-row invariant and assumed it would be TypeScript-only. The bootstrap carve-out: `circle_member_app_insert`'s `WITH CHECK` allows an actor to write their own `(lead, active)` row only when the circle has no non-removed members yet (`NOT EXISTS`), which is satisfiable only during creation (a real circle always has an active lead; the last lead cannot be removed; the transient window lives inside the creator's own transaction). It deliberately does **not** read `circle` — `circle_app_read` is members-only, so the just-inserted circle row is not yet visible to the app role there.
- **Q1 corollary — transfer-lead is one `UPDATE ... SET role = CASE ...` statement, circle row first.** `db/circles.ts`'s `transferCircleLead` takes `SELECT ... FOR UPDATE` on the circle row, updates `circle.lead_user_id`, then swaps both `circle_member` role rows in a single statement. Two statements cannot work: demote-then-promote trips `app_actor_leads_circle` in the promote's `WITH CHECK` (actor no longer leads); promote-then-demote trips the partial unique index (two active leads). The single `CASE` statement satisfies both — the index sees one lead at statement end, and the RLS subquery sees the actor still leading in the statement snapshot. Transfer to self is a no-op success; transfer to a non-active-member is 409 with no change.
- **Q2 — the circle view model excludes all four record counters and `created_at`.** `CircleView` (first real view model, `views/circles.ts`) is `{ id, name, leadUserId, memberIds }`. `no_shows` / `late_declines` are signal-category fields (same class as `Record.signal_score`, venue `licence_ref`) and stay out of every view model; `plans_hosted` / `plans_attended` are simply not needed by any C1 response, so shipping them now would only give F1 something to un-ship. `db/repositories/circles.ts`'s `CircleRecord` does not even select the counters — there is nothing at the view boundary to drop. F1 builds the public / contextual / self / moderator variants and extends the record if a moderator view needs the counters.
- **Q3 — no `domain/` module for circle membership; the seam is composed at the route.** Membership is `invited → active` and `active → removed` plus a role swap — 2–3 line guards, each already backed by an RLS policy and the partial index. A pure reducer would buy nothing, so the guards live in `db/circles.ts` next to the writes. The route pattern matches `app/api/auth/session/route.ts`: Zod parse → `getSessionActor` → `circles.membershipFacts` → `policy()` → `withActor(executor => { writes; recordAuditEntry })` → view model. `withActor` is imported directly from `@/db/scope/scoped` (A4 decision intact — not re-exported from `db/index.ts`). `db/circles.ts` takes the caller's `ActorTransaction` like `db/session.ts` and is in `TRUSTED_DATABASE_FILES` (not the ESLint 10-entry list — it imports no raw DB module).
- **Acceptance endpoint: `POST /circles/:id/members/accept`, a new named `INFERRED_ENDPOINTS` entry.** `docs/api.md` states "Invitee must accept" as a rule on the lead-only invite row but gives it no endpoint. New policy action `circle.acceptInvitation` (`{ membershipStatus }` → allow iff `'invited'`). `policy/actions.ts` exports `INFERRED_ENDPOINTS` (parallel to `MODE_ONLY_ENDPOINTS`); `tests/unit/policy.test.ts`'s completeness check is now 45 api.md + 2 modes.md-only + 1 inferred = 48, still checked in both directions. **No decline endpoint** — an invited member removing their own row via `DELETE /circles/:id/members/:userId` (the "member removing themselves" rule) is the decline path.
- **404 vs 403 split.** A non-member (including an invited-but-not-accepted user) gets 404 on every `:id` route — the circle's existence is not disclosed. A member who is not the lead gets 403 on a lead-only action: they already know the circle exists, so 403 leaks nothing, and §3's rule is about resources you may not *see*. The routes' shared `context.ts` does the visibility 404 gate; `policy()` still makes every allow/deny call (no inlined ownership check).
- **`circle_member_app_roster_read` (0009) is additive to 0004's `circle_member_app_read`.** 0004's policy gates on `app_circle_visible(circle_id)`, which is all-or-nothing — one blocked co-member and the whole roster (including your own membership row) vanishes, so `circles.get` and `membershipFacts` would break the moment a member blocks a co-member. The new policy restores the per-member view for an active member of the circle (`app_actor_hosts_circle(circle_id) AND app_user_visible(user_id)`), so a blocked co-member's row is still hidden but the rest of the roster is not. RLS policies combine permissively, so `unlisted_app` now has two SELECT policies on `circle_member`; non-members gain nothing.
- **`inviteMember` maps a bad-FK invitee id to 422 `unknown_user`.** The lead invites by ULID (there is no user list — the id comes from out of band). A `23503` from the FK becomes 422; `23505` from `circle_member_active_uq` becomes 409 `already_member`. 422 rather than 404 because the circle itself is visible to the lead — a 404 would misrepresent which thing was not found.
- **Correction to `0009_circle_access.sql:19`'s comment (frozen, not editable).** That comment says "no policy here reads `circle.lead_user_id`" — an overclaim, and it contradicts its own file. Two 0009 policies do read it, both deliberately and correctly: `circle_app_insert`'s `WITH CHECK` (`lead_user_id = app_current_actor_id()`) is the agreed circle-creation carve-out — the one place authorization is off the denormalized column, because no `circle_member` row exists yet at creation; and `circle_app_update`'s `WITH CHECK` reads `lead_user_id` to validate the *incoming* value is an active member, not to authorize the actor. What the sentence should say: the *lead-authorization check* (`app_actor_leads_circle`, used by `circle_app_update.USING`, `circle_member_app_insert`, `circle_member_app_update`) never reads `circle.lead_user_id` — it reads `circle_member(role='lead', status='active')`. The correction lives here rather than in the migration because editing an applied migration's text risks a drizzle `__drizzle_migrations` hash mismatch on any persistent DB (the same reason the 0006 TRUNCATE note went to Traps, not the SQL).

### C3

*Three things were put to the user before any code (agent-rules §6/§7); the answers, and the decisions built on them, are final.*

- **Q1 — "complete" is a write-helper, not an endpoint.** `docs/api.md` has no `POST /plans/:id/complete` and `policy/` has no `plan.complete` action; E1 (workers) owns completion and auto-cancel at `starts_at`. `db/plans.ts` exports `completePlan` and `closePlanAtStartsAt` — both call `transitionPlan`, persist, and have no route — for the E1 scheduled job to call; `tests/integration/plans.test.ts` drives them directly. Consequence, accepted by the user: a plan whose host circle alone has ≥ `MIN_PLAN_TOTAL` active members latches `viable_at` at publish and the 0004 introduction-ledger trigger populates with the host set immediately — no guests required. - **Q3 — PATCH immutability keys off the durable counter/latch trace (invitations/approvals are C7).** Editable while `draft`, or `published` with `held_count = 0 AND accepted_guest_count = 0 AND viable_at IS NULL`. - **Migration 0011 shape mirrors 0009.** `plan_app_insert` / `plan_app_update` RLS both `USING`/`WITH CHECK` `app_actor_leads_circle(host_circle_id)` — never a denormalised `lead_user_id` read. Table-wide `GRANT INSERT`; **column-scoped** `GRANT UPDATE` on exactly the lifecycle columns — `host_circle_id`, `accepted_guest_count`, `held_count` are not grantable (C5/C7 add those), `confirmed_total` is generated. So a C3 bug cannot move a plan's host or its guest capacity. `unlisted_admin` gets nothing on `plan`.

### C4

- **`GET /plans` wires the A3 `plans.feed`; no new visibility work.** The route only validates input and paginates — `plans.feed` already composes the block + enforcement predicates into the SQL through `scopedSelect` / `applyVisibility` (proven in `tests/integration/repo-block-scoping.test.ts`, re-asserted here via `toSQL()`). No second filtering path.
- **`district` is required (route-enforced, not in the repo type).** `GET /plans` 400s without `?district`. Rationale (decided by the user): a scraper must then enumerate districts — a coarse, small set — rather than pull the whole published set in one call, and it matches `docs/product.md`'s per-district "liquidity density". `PlanFeedFilters.district` stays optional in the repository so a future internal caller (a worker) is not forced through the API contract; the security property lives at the one exposed surface, with a deny-path test. `dateFrom` (inclusive) / `dateTo` (exclusive) / `venueType` stay optional.
- **Keyset pagination, cursor carries only the plan id.** `feed` resolves the boundary `(starts_at, id)` pair with a subquery against the DB's own stored row, *not* from a client-supplied timestamp — round-tripping `timestamptz` through JSON truncates sub-millisecond precision and would let a client re-see the row it just paged past (hit while writing the test). The cursor is base64url'd `{ i: <ulid> }`, Zod-validated on decode (malformed → 400 `invalid_cursor`). A forged / unseeable cursor id resolves the subquery to nothing → empty page, never an error and never a widening: every page re-applies the full visibility spec + business predicates. No `OFFSET`. No total count in the response (a count leaks the size of the filtered-out set — `docs/security.md` enumeration).
- **`FEED_PAGE_DEFAULT = 25` / `FEED_PAGE_MAX = 50` live in `db/repositories/plans.ts`, not `lib/config.ts`.** Same call as B1's `SESSION_TTL_SECONDS`: `bootstrap.test.ts` pins `lib/config.ts` to exactly the agent-rules §5 product parameters, and a page cap is an API/enumeration knob, not one of those. The route clamps to `FEED_PAGE_MAX`; `clampLimit` in the repo is defence-in-depth for any other caller. A `limit` above the cap is accepted and clamped (not 400); `limit <= 0` or non-numeric is 400.
- **Fourth view model: `views/plans.ts` `PlanFeedView`** — leaner than C3's `PlanView`. Drops `hostCircleId` (a circle handle a stranger cannot use — `GET /circles/:id` is members-only), `state` (always `published` in the feed), and every attendance-derived field including `viable` (a searcher sees a plan as pending, never who is in it). No venue name/address — the client resolves `venueId` through the public venue registry. A test asserts the serialized row has none of the dropped keys.
- **`applications_closed` plans are already excluded for free.** `plans.feed` hard-filters `state = 'published'`; the C3 closure path moves a plan out of `published` when applications close before `starts_at`, so it leaves discovery with no C4 code and no C3 change (decided by the user).

### C8

*The `message_thread` model change was escalated to the user as a schema contradiction and decided before any code (agent-rules §6/§7). It is Option A of four; the reasoning is final.*

- **The two-circle `message_thread` model was dropped (migration `0012`): `circle_a_id`, `circle_b_id`, `message_thread_distinct_circles_chk`, the two circle FKs and indexes all gone.** It came from `data-model.md` ("participants = all members of both circles"), which predates `MIN_HOST_CIRCLE = 1` and solo applicants (`application` is `applicant_circle_id` XOR `solo_user_id`). A viable plan of {1 host, 2 solo guests} — or {3 hosts, 0 guests}, which C3 ships — has one circle and could not store its thread even though viability is meant to open one. **The decisive point (put in the record at the user's instruction): the two-circle rule was never the anti-dyad guarantee.** Two distinct one-member circles satisfy `circle_a_id <> circle_b_id` and are a two-person thread. A dyad is barred only by `message_thread_min_participants_chk` (`participant_count >= 3`) and the FK to `plan.viable_plan_key` (which `enforce_plan_guards`'s set-time floor only lets exist for a plan whose `confirmed_total` was `>= 3`). Dropping the circle columns removed a constraint that was decorative for the invariant and wrong for the two-mode design. `db/schema/messageThread.ts` updated to match; `tests/integration/schema-thread-viability.test.ts` rewritten (loses only the `distinct_circles` sub-test, keeps every anti-dyad assertion).
- **`participant_count` is now trigger-maintained from `plan_participant_introduction` (0012) — the hard condition on Option A.** With the circle columns gone the whole anti-dyad guarantee would otherwise rest on a denormalised integer the application writes. Two triggers, both SECURITY DEFINER as `unlisted_migrator` (they read the migrator-only ledger): `message_thread_set_participant_count` BEFORE INSERT sets it from `message_thread_ledger_count(plan_id)` (ignoring any supplied value), and `reconcile_thread_participant_count` AFTER INSERT on `plan_participant_introduction` resyncs it when the ledger grows. The ledger is append-only, so the count only ever rises — matching the `viable_at` latch (an introduction is permanent). `message_thread_ledger_count` is **VOLATILE**, not STABLE: called from the AFTER trigger it must see the just-inserted ledger row. The resync `UPDATE` needs migrator SELECT + UPDATE policies on the FORCE-RLS `message_thread` (`message_thread_migrator_read`, `message_thread_migrator_participant_count`) — an `UPDATE ... WHERE` needs a SELECT policy to find the row *and* an UPDATE policy to change it (hit while debugging: a lone UPDATE policy silently matched zero rows).
- **This supersedes a sentence in `agent-rules.md` §3** ("A message thread requires two circle references and a viable plan"). That file is read-only; recorded as a user-authorized exception in Traps (above) so a future agent reading §3 finds the deviation explained.
- **Participant identity = `plan_participant_introduction`, not a `ThreadParticipant` table.** The ledger is already the append-only, per-plan, exactly-the-confirmed-attendees set (populated by the 0004 `reconcile_*` triggers on viability). New SECURITY DEFINER `app_thread_participant(plan_id)` — mirrors `app_shared_introduction_visible` but per-plan for the current actor — backs `message_thread_app_read` / `message_thread_app_insert` and both `message` policies. No membership table (§7).
- **Migration `0012` grants: `unlisted_app` gets table-wide `SELECT, INSERT` on `message_thread` and `message`, nothing else** (no UPDATE — `participant_count` is trigger-maintained; no DELETE — retention is E2). `message_thread` one-per-plan via `message_thread_plan_uq`. `unlisted_admin` gets nothing on either table — no admin path reads threads. Also folds in the carried-over C3 fix: `ALTER FUNCTION app_active_host_member_count(varchar) OWNER TO unlisted_migrator` (its failure mode under a narrowed `circle_member_admin_read` is a silent under-count, so it belongs with the population functions).
- **A5 fact `actorIsCircleMember` renamed to `threadParticipant`** across `policy/actions.ts`, `policy/rules.ts`, `tests/unit/policy.test.ts`. A fact named `circleMember` that a caller computes from the introduction ledger (a superset — solo participants are in no circle) is a misleading name in the one table where that costs the most. The route computes it from `threads.getByPlan` returning a row (RLS already enforced participation); `viable` from `plan.viableAt`.
- **`GET`/`POST /plans/:id/thread`.** Read: `plans.get` (404 if plan not visible) → `threads.getByPlan` (404 if `undefined` — no thread / not viable / not a participant, indistinguishable, §3) → `policy()` → list messages. Post: same gate → `withActor(postMessage + recordAuditEntry)`. The audit entry (`message_post`, resource `message_thread`) records `{ messageId }` and **never the body** (§3). `MessageView` *does* carry `body` — "never log" is about logs/audit, not about serving the message to the people in the thread.
- **`createThreadForViablePlan` (`db/threads.ts`) has no production caller.** Thread creation happens on the viability crossing, which lands in C7c. C8 ships and unit/integration-tests the path directly — same "nothing calls it yet" shape as A4's `recordAuditEntry` before B1 and C3's `completePlan` before E1. Recorded in Known gaps.

### A5

- **Every `moderation.*` allow-path is unreachable today, not merely untrusted.** `policy/rules.ts`'s moderation rules branch on a caller-supplied `resource.actorIsModerator: boolean`, the same design as every other resource fact in the table (see Decisions above — this is not a weaker trust boundary). But no moderator credential exists anywhere in this codebase (grepped `db/schema/`: nothing beyond the self-labelled `audit_log.actor_role` enum value covered by the A4 gap immediately above). `tests/unit/policy.test.ts` proves the rule is shaped correctly by supplying `actorIsModerator: true` directly; it does not and cannot prove any real caller can produce that value honestly. Until D4 gives moderators a real, distinct credential, nothing may call `policy()` for a `moderation.*` action with `actorIsModerator: true` and have it mean anything — that determination has nowhere to come from yet.
- **Nothing calls `policy()` yet.** Same shape as A4's "nothing calls `recordAuditEntry` yet": there are no route handlers or domain callers in this codebase (Phase C+), so A5 ships the rule table and its own tests only, matching `todo_agent.md`'s scope. The first real caller will also be the first place that has to supply the resource facts (`actorRole`, `sharesPlanContext`, `viable`, etc.) honestly from a repository/domain query — `policy/` assumes a caller does this correctly and cannot verify it.
- **Assembly has no rule, on purpose.** `POST /plans/:id/assembly/join`, `POST /assemblies/:id/confirm`, and `DELETE /assemblies/:id/leave` are named in `policy/actions.ts`'s `ASSEMBLY_ENDPOINTS` and asserted absent from the rule table by the completeness test. Assembly remains deferred per agent-rules section 5 and `todo_agent.md`'s "Not in scope"; if Assembly is ever built, its rules are new table entries, not a retrofit of an existing one.
- **Policy's resource facts are unverified inputs.** `policy()` trusts `actorRole`, `membershipStatus`, `sharesPlanContext`, `viable`, `isHostLead`, and every other resource field exactly as given. It is the future caller's job (a repository query, per A3's actor-scoped pattern) to compute these honestly; a caller that passes a fabricated fact gets whatever decision that fact implies. This is inherent to the "policy never queries anything" design agreed for A5, not a defect — but it means policy correctness depends on every future call site, not on this module alone.

### A6

- **Nothing calls the three machines yet.** Same shape as A4/A5's "nothing calls it yet": there are no route handlers or repository-backed domain callers in this codebase (Phase C+). A6 ships the reducers and their own unit tests only, matching `todo_agent.md`'s scope. The first real caller (a C3/C5/C7 route handler or its domain-boundary composition) is responsible for loading a `PlanSnapshot`/`PlannedApplicationSnapshot`/`TonightApplicationSnapshot` from the DB honestly, calling the right reducer under the plan row lock, and persisting the result — none of that is exercised here.
- **The plan reducer takes caller-computed counts and aggregates (`hostSize`, `invitedCount`/`includedCount`, `confirmedHostCount`), not raw membership/application rows.** It cannot verify that a caller's `hostSize` actually equals the count of active `circle_member` rows, or that `invitedCount`/`includedCount` reflect real `application_member` rows. Producing these honestly from repository queries is the first real caller's job (likely C3/C5/C6), the same boundary A5's policy module already has with its resource facts.
- **No wiring to `recordAuditEntry` (A4).** State-changing transitions have no audit-log call from `domain/` — agent-rules section 4 keeps `domain/` DB-import-free, so audit recording happens at the same future call site that loads/persists snapshots and enforces the row lock, not inside the reducers.
- **Tonight-mode's hosting-gate precondition ("unavailable to hosts below a minimum record threshold", `docs/modes.md`) is not encoded anywhere in A6.** It is not a plan-state or application-state precondition in the sense A6 owns (capacity, timing, mode immutability); per the still-open question in this file's Open questions section, what satisfies the gate is undecided, and C7b is where it will be enforced once answered. A6 does not adopt the previous agent's inference and does not gate `publish` or the tonight application machine on it.

### B1

- **No rate limiting and no idempotency keys on any `/auth/*` route.** `docs/api.md` marks `POST /auth/session` "rate limited hard" (5/15min) and agent-rules section 3 requires an idempotency key on every state-changing endpoint. Both need Redis (pinned, not installed) and are D5's task. Asked and confirmed this could wait — the stub credential has nothing real to brute-force yet.
- **No session TTL refresh / sliding expiry.** `expires_at` is set once at creation (and again at rotation) and never extended by activity. A session simply stops working 30 days after it was created or last rotated, even if used continuously. Revisit if that turns out to be the wrong shape for real usage patterns.
- **No "list my sessions" or "revoke a specific other session" endpoint.** `docs/api.md`'s Auth section names exactly three endpoints, and none of them exposes session ids to a client. `DELETE /auth/session` only ever revokes the session making the request. Individual revocation is proven at the repository/domain level (revoking one row leaves a user's other rows untouched); there is no route through which a user could ask to revoke a *different* one of their own sessions, because that would need a way to list them, which is out of scope here.
- **Nothing triggers `rotateSession` yet.** There is no privilege-change endpoint in this codebase to call it from (standing changes, verification completion, etc. are all later phases). B1 proves the mechanism directly (`tests/integration/auth-session.test.ts`); the first real caller is whichever future task changes a user's privilege level.
- **`getSessionActor` is unused by anything except `DELETE /auth/session`'s sibling, `getSessionContext`.** There is no protected route yet that needs "just the actor" (`GET /me` and everything else gated on `session` auth is Phase C+). It exists now because `todo_agent.md` names it explicitly as the seam `loadActorByUserId` sits behind, not because a second caller exists today.
- **Auth.js remains uninstalled** (see Decisions) — `docs/agent-rules.md` section 2 still pins it as part of the stack; this is a deliberate, asked-and-confirmed deferral, not an oversight, to be revisited once a real credential factor exists for it to configure.
- **No `POST /auth/session` behavior change on repeated logins.** Every successful login creates a brand-new session row; there is no cap on how many concurrent sessions one user can hold, and no "log out my other devices" semantics. Not asked for by any B1 done-when; flagging in case a future task assumes one exists.

### B2

- **No real vendor is integrated.** `lib/verificationVendor.ts`'s stub signs/verifies its own HMAC and never calls out anywhere; there is no vendor SDK, no webhook retry/idempotency handling beyond `verification_ref` being single-use, and no vendor-specific error taxonomy. Todo_agent.md explicitly forbids integrating a paid vendor in B2; this is the seam a real one plugs into (`VerificationVendor`), not a partial integration.
- **No rate limiting on `POST /verification/start` or `POST /verification/webhook`.** `docs/api.md` marks verification-start "3/day"; D5 owns rate limiting/Redis (pinned, not installed), same deferral B1 already recorded for `/auth/*`. Not built here, per todo_agent.md's explicit "do not build rate limiting (D5)".
- **No erasure or retention behaviour.** Confirmed out of scope with the user before starting (see Decisions). `identity_hash` is stored indefinitely for ban durability; nothing here implements the erasure-versus-ban-durability legal question from `docs/security.md` line 108, which remains open for **E2**.
- **No moderator/admin read path over verification data.** Nobody can look up a user's verification history or vendor session activity today — not a gap this task's done-when named, but worth flagging if a future moderation task (D4) assumes one exists.
- **A restricted/suspended/banned user's own verification write could silently no-op.** `user_system_verification_write` (migration 0008) lets a system actor UPDATE any row, but the pre-existing `user_app_read` policy's `app_user_visible(id)` predicate (unchanged, 0004) still gates which rows are visible at all under `unlisted_app`, and that predicate exempts only the *actor's own* standing check — a system actor is never "the row's own" actor, so it only passes when the target row's standing is `'good'`. In practice this is unreachable today: `verification.start`'s policy rule has no standing gate either, but a restricted/suspended/banned user's row would fail `app_user_visible` and the write would match zero rows, indistinguishable from "no matching session" (no error, no data corruption) — not a security hole, just an unhandled path. Widening `app_user_visible` (used by many other tables) to fix this is out of scope for B2; revisit if a real product need for re-verifying a restricted/suspended user surfaces.
- **`POST /verification/start` does not check whether the user is already `'verified'`.** A verified user can start (and even fail) another verification attempt; `completeVerification`'s verified-only-overwrite behavior (see Decisions) prevents a failed re-attempt from clearing their existing values, but nothing stops the attempt from being made at all. Not asked for by any B2 done-when; flagging in case a future task assumes re-verification is blocked.

### C1

- **No rate limiting or idempotency keys on any `/circles` route.** Same deferral as B1/B2 — D5 owns rate limiting, Redis is pinned but not installed, and agent-rules §3's idempotency-key requirement is unmet on these state-changing endpoints. `POST /circles`, invite, accept, remove and transfer are all replayable. `accept` and `transfer` are naturally near-idempotent (0 rows / no-op on repeat); `POST /circles` and `invite` are not (a second create makes a second circle; a second invite of an already-invited user is a 409, but of a removed-then-re-invitable user makes a fresh `invited` row).
- **`circle.record` counters (`plans_hosted`, `plans_attended`, `no_shows`, `late_declines`) are never written by C1.** They stay at their `0` defaults. C3/C7 plan-lifecycle work is where the domain layer increments them (agent-rules "record fields updated by the domain layer only" — C1 has no such path). No column grant for them exists yet; the C3/C7 migration that first needs to write them adds a column-scoped `UPDATE` grant, the same shape as 0009's `UPDATE (lead_user_id)`.
- **No "list my circles" or any circle-discovery surface.** `docs/api.md` has no such endpoint and §7 forbids person-browsing surfaces; a user reaches a circle only by already knowing its id (they created it, or were invited to it). `GET /circles/:id` is the only read. If a future task needs "circles I'm in", that is a new endpoint to design, not something C1 left half-built.
- **`inviteMember` reveals user existence to a circle lead** (422 `unknown_user` vs 204). Inherent to invite-by-id with no user directory — the lead already has the invitee's ULID from out of band. Not an enumeration surface (no listing, no search, ULIDs are not guessable), but noted: a lead can probe whether a specific ULID is a registered user. Revisit if D5's abuse work wants invite attempts rate-limited.
- **The bootstrap carve-out in `circle_member_app_insert` trusts `NOT EXISTS (non-removed member)` read under RLS.** If `circle_member_app_read`/`circle_member_app_roster_read` ever hid *all* of a circle's member rows from an actor (e.g. a future policy change), the carve-out's `NOT EXISTS` would read empty and an actor could insert themselves as `(lead, active)` into that circle — but only if it has no active lead, which `circle_one_active_lead` + the "last lead cannot be removed" rule make unreachable for any real circle. The partial unique index is the hard backstop; the `NOT EXISTS` is the intent-documenting soft guard. Flagging so a future migration author does not weaken the index assuming the policy alone suffices.
- **`context.ts` lives in `app/api/circles/` as a non-route module.** Next only treats `route.ts` as a route, so this is fine, but it is the first shared helper file under `app/api/`. If more accumulate, a `lib/api/` home may be tidier.

### C3

- **No rate limiting or idempotency keys on any `/plans` route.** Same deferral as B1/B2/C1 — D5 owns rate limiting, Redis is pinned but not installed. `docs/api.md` sets "Plan creation 5 / day". `POST /plans` is replayable (a second call makes a second draft); publish / cancel / close are naturally near-idempotent (a repeat hits the reducer's state guard and 409s); `PATCH` is last-writer-wins.

- **`app_active_host_member_count` (0011) is owned by `unlisted_admin`; `unlisted_migrator` is the better home.** It was written to mirror `app_actor_leads_circle` / `app_actor_hosts_circle` (0009 / 0004), the actor-circle-membership SECURITY DEFINER helpers — but those fail *loud* under a future narrowing of `circle_member_admin_read` (a lead check that finds no row denies the write), whereas a count fails *silent* (an under-count makes `publish` reject feasible plans and understate `confirmed_host_count`, skewing the viability latch). Its purpose — see the true membership regardless of the actor's block filter — is exactly what the migrator-owned population functions exist for, and they rely on `circle_member_migrator_population_read USING (true)`. ### C8

- **`createThreadForViablePlan` has no scheduled/route caller.** Threads are created on the viability crossing — C7c. `db/threads.ts` ships the path, `tests/integration/threads.test.ts` drives it directly. C7c must call it inside the plan-row-locked transaction that stamps `viable_at` (C3's `publishPlan` for the host-only-viable case; C5/C7 acceptance otherwise), so the thread and the latch commit together.
- **`participant_count` only grows; nothing shrinks it, by design.** The ledger is append-only and a withdrawal never removes a row (the `viable_at` latch semantics — an introduction is permanent). So a thread's `participant_count` can exceed the count of attendees who are *currently* confirmed. That is intended (the thread membership is "everyone ever introduced on this plan"), but flagged because a future reader may expect it to track live attendance — it tracks introductions.
- **No message pagination.** `GET /plans/:id/thread` returns every non-deleted message ordered by `(created_at, id)`. `docs/api.md` Messages specifies none and F3 seeds little, but a long-running thread returns unboundedly — same shape as `GET /venues` being unbounded. Add a cursor (the discovery keyset is the pattern) if threads get chatty.
- **No message edit or delete.** `message` has `edited_at` / `deleted_at` columns (0000) but 0012 grants `unlisted_app` only `SELECT, INSERT`. Editing/retracting a message and the retention worker's thread deletion are later (E2 owns retention). `GET` already filters `deleted_at IS NULL` so a future soft-delete path needs no read change.
- **No rate limiting on `POST /plans/:id/thread`.** `docs/api.md` marks it "Rate limited" (Messages 60/hour); D5 / Redis, same deferral as every other write endpoint.
- **The thread has no explicit close/archive.** It exists from viability until the retention worker (E2) deletes it `retention_delete_after` (set at plan completion). A cancelled-after-viable plan keeps its thread until retention — consistent with "the introduction is permanent", flagged so E1/E2 handle the `retention_delete_after` stamp.
- **`db/repositories/threads.ts` is the second spec-less read repository in `TRUSTED_DATABASE_FILES`** (after `venues.ts`). It runs plain `SELECT`s under `withActor` because access is entirely RLS-decided (`app_thread_participant`), with no counterparty-user `VisibilitySpec` to feed `scopedSelect`. Same deliberate exception, same "do not copy onto a social table with a counterparty" caveat.
